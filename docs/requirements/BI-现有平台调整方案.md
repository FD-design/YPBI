本文只写现状和改造，不重新定义产品需求、指标公式或事件契约，也不直接修改前端、后端、接口契约或部署代码。

## 1. 总体判断

当前 YPBI 已具备“配置卡片、组装模板、调用部分真实 API、展示趋势/排行/表格”的基础，但产品对象主要按现有接口和代码结构形成，尚未成为“权威数据资产 → 分析 → 已保存分析 → 看板组件 → 看板”的稳定链路。

最重要的调整不是换导航文案，而是同时完成四件事：

1. 按业务判断重组看板，不按 API 或实现页面拆分。
2. 把指标、事件、分析、组件和看板拆成单义对象，并建立真实引用。
3. 清理正式路径中的 Mock、固定数组、推算数量和缺失补 0。
4. 把“界面可选”改成“数据能力真的支持”；不支持的组合在查询前阻止。

指标映射与行为分析可以并行推进。事件分析页面不必等待全部指标接入；真实漏斗依赖事件事实、身份、顺序、窗口和数据水位，但不依赖事件分析页面先上线。

目标 PRD 按理想完整产品规划：凡权威指标体系已登记的指标，均可进入目标看板清单，不因待验数、口径待确认、埋点草稿或需平台加工而从需求中删除。本方案负责逐项记录其当前 API、数据粒度、支持状态、缺口和验收动作；只有完成真实查询与验数的指标才能进入普通用户正式界面。现状缺口不得反向删减合理需求，理想需求也不得被描述成现有能力。

## 2. 当前问题与目标差异

| 当前问题 | 已核对事实 | 目标调整 |
|---|---|---|
| 看板按接口/模型拆分 | 经营、内容、搜索、支付、留存等直接成为看板或“分析模型” | 业务归属跟随指标体系分类；单张看板围绕业务判断组合 |
| “分析模型”混入业务主题 | 现有模型名称是内容、搜索、支付、获客等业务域，不是分析方法 | 改为业务主题/数据能力模型；指标、事件、漏斗才是分析类型 |
| 系统模板实际是正式看板 | 用户直接读取系统模板中的线上数据 | 迁移为官方看板；V1 不另建模板对象和模板入口 |
| 卡片承担三类对象 | 同时保存查询、复用资产和看板容器 | 拆成已保存分析、看板组件、看板本地展示配置 |
| “漏斗”只有阶段汇总 | 现有结果无法证明同一用户依序完成步骤 | 改名阶段量对比；新增真实用户级有序漏斗 |
| 普通看板和专用页面混在一起 | 6 张配置驱动看板与 3 个专用实现页面都叫系统模板 | 按用户任务定性为看板/分析/报表；实现方式只作为迁移属性 |
| 数据字典重复权威口径 | 本地指标定义、字段帮助和服务端注册表存在多份公式说明 | 删除产品级重复字典；指标进指标中心，事件/属性进事件中心，API 连接进数据源维护 |
| 筛选控件大于数据能力 | 查询协议声明 `filters`，但当前通用请求固定发送空对象，服务端/Adapter 未实际应用 | 筛选项由能力声明生成；不允许界面显示后由接口静默忽略 |
| 正式路径仍混入模拟信息 | 导出、下钻趋势、引用数量、加载进度等存在 Mock、固定数组或推算 | 全路径改用真实结果与真实关系；不能支持时显示状态或隐藏入口 |
| 数值与涨跌显示不统一 | 当前页面分别使用 `toLocaleString`、`toFixed`、硬编码人民币/“万”等方式，部分卡片依赖本地 `positive` 配置用红绿判断好坏 | 建立全局数值格式层；卡片可紧凑显示，提示/表格/导出保留精确值；没有权威指标方向、目标或阈值时只中性展示变化，不判定正常/异常 |
| 工作区写入没有最小身份边界 | `/api/bi/workspace` 匿名读写同一份全局文档，没有 Owner、作用域或写权限校验 | 建立稳定身份和阅读者 / 分析者 / 维护者三档最小操作角色，并为个人与官方对象分别建立归属和服务端写权限；未完成角色映射的账号按阅读者处理 |
| 工作区保存会静默覆盖 | 当前工作区对象没有 `revision` 或等价并发条件，后写入会覆盖先写入 | 所有可编辑看板和共享来源分析使用版本条件写入；冲突时返回并发错误，不自动覆盖 |
| 现有业务详情不是按卡片条件下钻 | 当前详情路由只接收 PID、日期和分页，未携带所点指标、查询快照或筛选；部分趋势使用固定数组，并暴露用户标识 | V1 从正式路径关闭该入口并移除固定趋势；未来若建设独立“用户日明细”，必须另行确认字段白名单、权限、脱敏和审计 |
| 每日扫数依赖外部静态 HTML | 用户提供的每日分析文件把多产品、多指标和结论预先写入页面；没有 YPBI 查询、个人配置保存或真实看板引用 | 在看板中心建设“指标速览”独立对象；只读取正式查询服务，支持每人多份命名配置，不迁入静态数值、自动结论、广告指标或文件内产品清单 |

## 3. 导航与对象迁移

| 当前入口/对象 | 目标去向 | 迁移动作 |
|---|---|---|
| 看板中心 | 看板中心 | 调整为公共概览、我的概览、指标速览、我的收藏；公共概览使用“业务分类 → 看板”二级树，指标速览管理个人多份命名扫数配置 |
| 系统模板 | 官方看板 | 保留真实配置与数据，统一改名并按业务判断重新归类 |
| 我的模板 | 我的看板 | 迁移存量对象；需要最小用户身份和对象归属，不依赖完整角色系统 |
| 分析中心的卡片库 | 已保存的分析 | 区分指标、事件、漏斗来源；补齐查询定义、版本、失效和真实引用 |
| 创建分析卡片 | 指标分析、事件分析、漏斗分析 | 三类分析作为分析中心独立二级入口；指标分析只读取已接入、已验数的权威指标并提供轻量查询、对比和维度拆解，不承担指标创建或公式维护；按来源进入各自配置与结果页 |
| 模板管理 | 看板自身编辑 | 普通看板从自身进入编辑；V1 移除独立模板入口，原模板分别迁为官方或个人看板 |
| 数据字典 | 数据中心 | 指标进入指标中心；事件及属性进入事件中心；不保留重复总字典 |
| 数据源维护 | 管理 / 数据源维护 | 移至底部管理分组；保留已接入接口/数据源的连接配置、检测和运行状态 |

维度与分类不单独堆成第三个中心：指标分类和可用维度在指标中心展示，事件业务模块和属性在事件中心展示，分析页根据所选对象计算共同可用项。原数据字典中的原始 API 字段如需维护，应作为数据源连接的技术详情，不冒充产品指标或事件。

指标中心完整同步权威指标体系的一级分类、二级分类和指标；公共概览只呈现“一级分类 → 看板”，不把二级分类再做成第三层导航。每张官方看板保存一个所属一级分类及一个或多个覆盖二级分类，允许把同一一级分类下业务判断相近的二级分类合入一张看板，不机械生成“一类一板”。分类允许后续调整：空分类不显示；拆分、合并或删除前先迁移所属看板；分类变化只改导航归属与覆盖标签，不自动改写看板指标和组件；迁移保留稳定看板 ID，避免收藏、链接和配置失效。

## 4. 现有看板迁移方案（已确认）

目标看板清单及建设顺序已经确认，核心经营总览及其余十张正式业务看板均已完成详细产品确认。存量迁移固定采用本节映射：系统模板迁为官方看板，个人模板迁为我的看板，专用页面按真实业务判断并入对应正式看板；资讯与问卷暂不迁入正式目录。只迁移真实配置、稳定对象关系和已准入数据，不复制 Mock、固定数组、假状态或旧名称。逐项权威映射、真实查询和验数仍是指标进入正式环境的独立门槛。功能使用概览的产品规则已经确认，但稳定指标引用和真实查询未就绪前不得发布空看板。

| 专项运营 / 资讯、问卷 | 暂不迁入正式目录 | 先明确目标用户、频率和可执行动作 | 当前通用记录表不足以证明是看板需求 |
| 外部每日数据分析 HTML | 指标速览的需求参考，不直接迁移 | 复用“指标按行、PID 切换、当前值及日周变化”的阅读方式；改为权威指标选择、真实查询、个人多份配置和分析/看板联动 | 文件数据与结论均为静态内嵌，包含本阶段排除的广告内容，不能作为接口、PID 或指标清单 |

当前 3 个专用实现页面是：`ContentDashboard`、`ChannelDashboard`、`SpecialDashboard`。它们直接维护专属查询与布局，不通过普通模板/组件引擎。专用代码实现不等于报表；是否属于看板、分析或报表必须按用户任务判断。

广告不进入本阶段任何看板、指标速览、分析创建、已保存分析候选或业务导出；指标中心仍可同步展示权威源中的广告指标及其状态。现有看板组件、模板、指标选择器、能力白名单和本地字典中的广告候选都纳入后续迁移排查，具体隐藏或下线由开发实施任务处理。

## 5. 看板、组件与分析的实现差异

| 目标能力 | 当前事实 | 改造要求 |
|---|---|---|

## 7. 数据能力与接口映射

### 7.1 状态定义

| 状态 | 判定标准 |
|---|---|
| 现有接口完整支持 | 数据、粒度、平台和所需查询条件均由当前正式能力提供 |
| 现有接口部分支持 | 只覆盖部分数据、粒度、平台、筛选、下钻或导出要求 |
| 指标本身已定义，但当前 YPBI 无数据能力 | 权威指标已存在，但 YPBI 没有正式数据链路 |
| 需要新增埋点、接口或加工层 | 数据基础或服务语义不足，不能靠前端拼接实现 |

Mock、示例和纯图表预览不计入正式支持。

每项缺口除上述支持状态外，还必须标注实际建设类型，避免把所有问题误写成“要埋点”：`应用 API/存储` 用于目录、收藏、引用和并发保存；`查询 API` 用于筛选、分组、事件分析和漏斗查询；`加工层` 用于周期聚合、身份归一和有序组链；只有运行侧确实没有采集对应事件或属性时才标记 `新增埋点`。同一项可以包含多种建设类型，但必须逐项列明。

| M081 活跃用户观影率 | 本地 `viewRate`，由当前查询中的 `viewerCount` 与 `dau` 生成；来源为日汇总或实时接口 | 按日或实时时点、逐 PID；已有周期重算实现但未绑定权威指标 | 现有接口部分支持 | 验证分子分母与权威口径一致；补共同水位、正式大盘及同周期比较，不能平均每日百分比（映射治理、查询 API） |
| M036 有效观影率 | 当前指标注册表、日汇总和实时 Adapter 均无对应正式指标 | 无 | 指标本身已定义，但当前 YPBI 无数据能力 | 依赖有效观看与起播事实建立统一加工结果，提供按日与周期结果、PID/大盘范围和验数状态（加工层、查询 API；缺采集时再补埋点） |
| M020 注册用户D1留存率 | 本地 `retentionD1`；`analytics.query` → `/api/bi/analytics/query` → `retention.daysPlus` `/api/admin/statistics/reletionsStatPlus/getDays` | 逐 PID、按 D0 注册 Cohort 日期；支持加权汇总候选实现 | 现有接口部分支持 | 修正 D1 缺失被转成 0 的现状；补成熟水位、等价 Cohort 对比、权威 PID 映射和正式大盘能力并验数（Adapter 修正、加工层、查询 API） |

当前内部结果中的 `platform` 多处实际承载业务 PID 的展示名称，不等于客户端平台 Android/iOS/Web；逐项映射时必须先完成语义迁移。现有“全部平台”会逐 PID 查询后合并，尚未定位到可证明跨 PID 去重、统一币种和完整覆盖的正式大盘整体服务，因此 9 项均不得把当前合并结果直接标为“大盘”。

本次核对时权威事件均为草稿，因此当前没有事件可直接进入正式事件分析或真实漏斗。埋点文档只证明产品定义与契约记录，实际事件集合必须由开发交付的采集和查询服务证明；后续只有同时满足“权威源已登记、开发已上线、有真实数据、YPBI 可查询、数据已验数”才开放选择。文档有而运行侧没有的事件标记待开发或未上报；运行侧有而权威源没有的事件标记未治理，完成确认并回写权威源前不得进入正式分析。现有固定事件名或阶段字段不得据此自动认定为正式事件。

事件与漏斗服务还必须同时满足：事件次数先按权威稳定事实键去重；身份缺失记录不进入用户类统计并返回身份覆盖率；数值属性返回有效和排除样本数；漏斗成熟水位取步骤、身份、筛选、分组和跨步属性全部依赖的共同最小可靠水位并计入迟到缓冲；事实唯一键只负责去重，同时间戳没有单调事件序号或明确因果顺序时不推断先后；没有跨 `pid` 身份去重时不合并用户数。

首批候选核对范围只从权威源当前有效、非广告指标中动态筛选，不用静态区间默认全量纳入；已废弃指标（包括本次核对发现的 M004、M017）必须排除。候选只代表待核对，不代表已接入。

## 8. 现有公式治理

当前 YPBI 公式主要来自上游后台汇总字段、服务端本地指标注册表、前端本地字典/字段帮助，以及为现有接口做的日均、累计人天和加权比率修正；并非稳定同步自当前全站指标体系。

这些实现不一定全部错误，但没有绑定权威指标 ID 和版本，不能证明口径一致。治理顺序：

1. 盘点本地指标和所有分析/看板引用。
2. 为每项寻找权威 M/DM ID；无对应项只登记待确认，不在 YPBI 自建正式指标。
3. 用户确认接入后核对字段、聚合、去重、窗口、时效和可用维度并验数。
4. 对齐项改为引用 ID/版本；冲突项先记录差异，不静默改权威口径。
5. 清理前端、服务端和文档中可独立修改的重复公式说明。

优先核对 `newUsers` 的首活/注册含义，`dau/viewerCount/payerCount` 的日均与区间人数差异，`payRate`、`arpu`、`arppu` 的分母与窗口，以及访问/下载/注册统计主体不对称问题。具体口径仍以权威指标体系为准，不在本文复制。

### 9.1 开工策略（终审结论）

采用“同仓分层迁移：保留技术与数据接入底座，重做产品领域层”的方案。它不是在旧页面上继续堆功能，也不是另起技术栈全部重写：保留已经验证的数据源连接、请求保护、适配器、图表和工程基础，在同一仓库新增目标对象、查询契约、身份权限、路由和页面；新旧链路通过功能开关或独立路由并行核对，完成一个业务闭环后再切换对应旧入口。

| 方案 | 优点 | 主要风险 | 结论 |
|---|---|---|---|
| 全量重做 | 目标结构最干净，没有旧页面约束 | 重复建设已验证的接口适配、错误处理、图表和测试底座；一次切换风险高 | 不采用 |
| 直接在旧结构上迭代 | 表面启动快，短期改动少 | 旧 `Workspace → Template → Card`、本地分析模型和匿名全局保存会持续污染新对象；后期迁移与回归成本最高 | 不采用 |
| 同仓分层迁移 | 复用真实能力，同时隔离旧对象债务；可按闭环灰度和回退 | 需要先建设领域层与迁移边界，前期看起来不像在快速堆页面 | 采用 |
| 新旧两套长期并存 | 对旧用户影响小 | 双写、双口径、双入口和长期维护成本不可控 | 只允许作为短期迁移状态，不作为目标架构 |

判断边界：可以复用的是“如何安全访问上游并呈现查询结果”；必须重做的是“有哪些产品对象、谁能操作、如何表达查询、如何保存和复用”。禁止继续把目标功能直接写入现有 `src/main.tsx`、旧卡片 Schema 或本地指标注册表。

`saved_analysis` 至少记录 `scope`、`owner_id`、`maintenance_scope_id` 和 `revision`：`personal` 必须绑定当前 `owner_id`，`maintenance` 必须绑定服务端认可的维护范围，二者互斥。个人来源转入官方场景只能复制，不能原地改作用域或改 Owner；复制与 `dashboard_component` 建立引用必须使用同一服务端事务。实际维护范围标识由第 12 节的身份权限源落定，不得以前端角色、名称前缀或固定账号代替。

### 9.3 开工前安全门槛

下列问题是现有代码事实导致的 P0，不得留到页面做完后补：

1. `/api/bi/workspace` 当前匿名读写一份全局对象；新对象写入必须先接稳定用户身份、角色、Owner / 维护范围、PID 数据范围和 `revision` 条件写入。服务端必须拒绝非维护者创建或更新维护范围来源，并拒绝官方看板引用个人或无归属来源，不能只靠前端隐藏入口。
2. 通用数据源查询必须校验该数据源是否允许被 BI 使用、调用者的数据范围和参数白名单；管理接口或受限源不能只凭数据源 ID 被查询。
3. 当前用户详情/下钻在缺少对象条件、权限、脱敏和审计时关闭，不迁入 V1 正式入口。
4. 图表 tooltip 禁止拼接未转义 HTML；CSV/XLSX 文本字段须防公式注入，完整导出由服务端按同一查询快照生成。
5. 生产进程使用最小权限用户和正式静态资源服务，不以 root 或 Vite preview 作为最终运行方式。

### 9.4 分阶段实施与首个闭环

### 9.5 开工架构健康检查（2026-09-08）

本次检查覆盖产品目标与核心链路、前端与服务端模块、领域对象、查询与持久化、上游 API、部署和现有测试。当前技术栈及已验证的上游 Adapter 可以继续使用，50 个非测试 TypeScript / TSX 文件的静态相对导入未发现循环依赖；因此没有整体重写的必要，继续执行“同仓分层迁移”。本节只记录代码事实、风险和改进顺序，不新增产品需求，也不复制指标或事件口径。

第 3～8 节的对象迁移、数据映射和现有看板去向均用于指导目标产品层重建，不表示继续沿用旧产品模型。当前核心链路仍是旧 `Workspace → Template → Card` 整体保存；目标核心链路是“权威目录 → 分析查询 → 已保存分析 → 看板组件 → 看板 → 同快照查看 / 导出 / 当前视图链接”。现状前端主要集中在约 2,500 行的 `src/main.tsx` 和约 3,100 行的全局样式，服务端由 `server/app.ts` 集中组装路由，查询通过上游 Adapter 获取真实数据，工作区使用 PostgreSQL 或文件 Store，部署由 Nginx、systemd 和当前 Vite preview 组成。以下风险按是否阻断正式 V1 使用分级：
