## 权威边界

- 指标 ID、名称、版本、分类、维度和口径只引用[全站指标体系](../../../全站埋点与指标体系/全站指标体系.md)。
- 事件 ID、名称、版本、属性和状态只引用[埋点权威源](../../../全站埋点与指标体系/H5全站埋点规范-协作主文档.md)。
- YPBI 只决定选择哪些指标/事件、如何分析和展示，以及当前真实数据能力；不复制公式或事件契约。
- Mock、示例数据和纯界面 Demo 不计入正式能力。
- 广告 BI、完整权限、复杂版本和审批不在当前 V1 范围。
- UI 实现继续遵循[已确认问题与防回归规则](../UI-已确认问题与防回归规则.md)；该文档只约束已存在或 PRD 已确认的模块，不得据其历史名称新增或保留功能。
- 本对话只维护产品需求与差异，不修改 `src`、`server`、`contracts` 或 `deploy`。

## 写法与状态

- 本项目使用面向 AI 生成与持续迭代的需求格式，不套用写给传统研发评审的通用 PRD 模板或外部需求说明规范；当前总 PRD 的章节、对象关系、功能点、状态、数据能力和验收门槛就是唯一写作结构。
- 写作优先级为：AI 无聊天也能准确生成 > 产品经理与同事能快速读懂 > 形式完整；不为凑模板增加用户故事、五章结构、重复数据字典、逐按钮说明或过程性文字。
- 每个主要模块必须有精简“功能点清单”，单看清单即可理解功能主体。
- 每个模块采用分层阅读：先呈现目标、功能点与页面结构，再展开交互、状态、数据边界和验收；读者无需查找聊天记录才能理解。
- 只有影响实现的对象关系、计算、交互、布局、状态和边界才展开；讨论过程和竞品体验过程留在对话。
- 总 PRD 内嵌线框用于固定页面信息层级和操作边界；独立 Demo、竞品截图和示例数据只用于辅助理解，文字规则仍是开发依据。
- 待确认问题先在对话中逐项解决，再写入总需求；不得为新问题随意增加功能文档。
- 每轮需求讨论确认后，维护者必须主动回读本轮对话，将会影响 AI 实现的功能点、默认值、字段/名称、展示形式、交互、状态、边界、依赖和数据缺口及时写入总 PRD 或调整方案，不等待用户重复提醒，也不把聊天记录当作开发依赖。
- 进入下一议题前执行一次覆盖核对：每项已确认决定均能定位到文档；每项未确认决定均只出现在待确认区；新规则与旧规则冲突时更新当前规则并保留版本记录。文档可以精简表达，但不得省略会导致 AI 猜测或实现分歧的细节。
- 如果总文档将来确实大到影响使用，必须先经用户确认才能拆分。

需求状态统一使用：草稿、待确认、已确认，可开发、开发中、待验收、已验收、已上线、已废弃。整份 PRD 使用章节级状态；未经用户明确确认，不得把对应章节标为“已确认，可开发”。
